# 五手两打的开局轮换与筛选

2026-10-10。自动三子开局从逐步固定取平衡首选，改为完整开局池与随机方向。只用于五手两打的 AI 三子批次（附身我方开局或对弈 AI 开局），不替换对方录入、手动记录、自定义中盘或其它规则的操作。

## 筛选方法

枚举中央 3×3 的第二子和中央 5×5 的第三子，按八种旋转 / 镜像归一化，得到 26 类标准开局。规则来源：[RIF Classic Rule](https://www.renju.net/rule/1/) 与 [26 Renju Openings](https://www.renju.net/openings/)。第一子为天元，颜色顺序固定黑、白、黑。

直接在 Node 中加载本站发布的单线程 SIMD WASM，没有浏览器或界面自动化。实际运行版本以原始 JSON 的 `runtime` 字段为准。使用固定 Rapfi 提交 `1be1551ced57e38d53ed58f6d74bf6f8b4bdc230`、rule 4、黑白专用 mix9svq 权重、256 MiB 搜索缓存，原生 pondering 与数据库关闭。模型拼合后核验清单里的 SHA-256；发布资源另外通过 `npm run check` 全量核验。

每类开局分别用 1 秒、3 秒预算执行以下流程，共 52 次开局延续评估：

1. 清空搜索哈希，录入三子并保持颜色归属。
2. 由现有推荐流程搜索白棋第四手。
3. 搜索黑棋两个合法、非对称等价的第五手提案。
4. 分别把两个提案落盘，搜索白棋回应，取白方估算胜率较高的那个。
5. 计算黑方估计 `p`，按对方可换色的情形，以 `min(p, 1-p)` 筛选开局。

每步都重置限制点，避免黑棋提案范围影响之后的白棋搜索。提案预算按现有应用逻辑分配；两种假想第五手的回应各使用完整预算。所用第四手与提案来自有限搜索，不是完整 RIF 开局博弈求解。

门槛为两个预算下 `min(p,1-p) >= 0.35`，共有三类达到初筛门槛。然后以每步 10 秒复核这三类；`97:142` 的较弱一方估计降至 25.35%，被排除。最终只保留下面两类。

| 规范开局键 | 三子索引 | 1 秒黑方估计 | 3 秒黑方估计 | 10 秒黑方估计 | 不同方向 |
|---|---|---:|---:|---:|---:|
| 97:80 | 112, 97, 80 | 46.13% | 54.12% | 50.62% | 8 |
| 96:80 | 112, 96, 80 | 37.99% | 40.61% | 49.75% | 4 |

这些数值只用于筛选，不是对某个真人的胜率，也不证明局面严格平衡。原始搜索未隔离操作系统其它任务；规范方向只测了规定的三个预算，不能据此宣称所有方向的有限搜索评估都相同。旋转 / 镜像的规则等价性由全部方向的合法落子及两个换色分支检查覆盖。没有旧版与新版对战棋力或 Elo 结论。

## 使用与恢复

先选择开局类，再从该类的不同方向中随机选完整三子；不会把第二、第三子独立随机拼接。首次为空盘时，避开上一次完成的开局类；其它近期类降低抽取权重。方向变化不作为新的开局类记入历史。第三子真正提交后才记录使用历史，取消未完成批次不会提前消费。

当前计划与对局自动存档一起保存。刷新、重试或恢复匹配的部分开局时继续同一组三子；历史元数据损坏会忽略，存储不可用时保留内存历史，不阻断对局。不匹配开局池的旧部分记录回退到原有搜索。已落棋子不因开局池而移动，JSON 棋谱与复盘仍以实际操作事件为准。

自动已选开局无需模型加载或额外搜索即可显示。换色选择继续由用户按外部实战确认，第四手、第五手提案、选案和正常对局继续使用原有引擎策略。界面没有新增开局设置或弹窗。

## 复现与验证

```sh
npm ci
npm run check
node scripts/opening-pool-eval.js reports/opening-pool-recheck.json 1000,3000
node scripts/opening-pool-eval.js reports/opening-pool-reference-recheck.json 10000 97:80,96:80,97:142
npm test
```

再次运行同一输出路径会跳过已完成的类 / 预算组合；引擎适配实现变更时需要换一个输出文件。计时搜索的具体数值可能随设备和缓存状态变化，重新筛选应重新检查门槛，不直接沿用这里的结论。

原始数据：[26 类两档筛选](./opening-pool-evaluation-v1.json)、[三类长搜索复核](./opening-pool-reference-v1.json)。JSON 保存实际棋点、两种提案的深度 / 节点 / 用时 / 杀棋信息及评估，包含案例内容与适配实现的 SHA-256。

专项 Node / jsdom 测试覆盖批次一致性、真实开局类的近期去重、部分计划刷新恢复、损坏元数据与存储失败、外部开局隔离、所有方向的合法性、换色归属、编号、内联选择与新局，以及数据筛选门槛。没有进行浏览器测试。
