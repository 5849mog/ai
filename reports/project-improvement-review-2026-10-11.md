# 五目项目改进评审报告

**评审日期：**2026-10-11

**评审基线：**`main`，提交 `42c5bd2`

**评审范围：**主页面与连珠跟随模式、搜索预算、存档、Service Worker 离线资源、现有测试与最近两批棋力对照。本文是代码和数据评审，不代表在真实手机网络或真人对局中完成了新一轮验收。

## 一、结论摘要

项目已经远超基础五子棋页面：它有 freestyle 与连珠两套规则流程、正式开局协议、附身与手动记录、自定义摆局、截图导入、复盘、最近对局归档、离线运行和设备布局验收。当前不需要大规模重写，也没有证据支持增加一个新模型或直接宣传棋力提升。

下一轮最值得投入的是五件事，按收益和证据排序：

1. **把离线缓存改成按规则和设备能力按需准备。**现在首次离线准备会缓存两套引擎的所有构建和模型，manifest 文件合计约 **33.0 MiB**；大部分只玩 freestyle 的手机用户不需要连珠模型。
2. **专门处理短预算搜索。**600 毫秒配对赛中，自适应为 **3 胜、1 和、8 负**，固定搜索为 **8 胜、1 和、3 负**。当前自适应流程里的固定阶段预算，在短预算下会相互挤占时间。结果样本还小，足以触发专项改进和复测，不足以证明普遍棋力差距。
3. **为 PR 建立自动质量门。**仓库已有测试和完整性检查，但没有发现 GitHub Actions 工作流。每次合并目前仍依赖人工记得运行相应命令。
4. **降低棋谱备份与跨设备转移成本。**最近对局最多保留 50 局，数据只在本机浏览器；逐局导出存在，但批量备份仍要用户逐条处理。
5. **用真实对局逐步建立反馈闭环。**现有自我对弈不能替代真人实战；应从自愿、本地、可删除的记录汇总开始。

## 二、项目当前基础

产品定位清楚：GitHub Pages 托管，AI 在浏览器本机运行，无需后端（`README.md:19–27, 78–88`）。连珠模式覆盖跟随外部棋局、手动记录和 AI 对弈；截图导入、棋谱导入、复盘和最近对局已存在（`README.md:7–17, 46–50`）。因此，下一步应集中在加载成本、短时搜索表现、自动验收与数据保全，而不是再增加一批功能开关。

项目已有 `npm test`、`npm run check`、浏览器验收与真实 WASM 专项脚本（`package.json:7–32`）。最近本地验证中，Node 测试为 29/29 通过，`npm run check` 也通过。问题是这些工具尚未组成合并前的自动门槛，专项浏览器测试与发布验收仍需人工挑选。

## 三、优先改进项

### 1. P1：按需缓存引擎和权重，降低手机首次准备成本

**代码依据。**Service Worker 的 `warmEngines()` 遍历 Rapfi 与 Renju 两个 manifest 的全部文件，并以每组三个文件的方式下载（`sw.js:33–49`）。Rapfi manifest 含四种单 / 多线程、SIMD / 非 SIMD 构建和共享数据；Renju manifest 含黑白两套权重。按 manifest 字节数，Rapfi 资源合计约 **14.1 MiB**，Renju 资源约 **18.9 MiB**，两者合计约 **33.0 MiB**。README 也说明首次准备会缓存四种引擎构建（`README.md:82–90`）。

**用户影响。**移动网络较慢或存储空间紧张时，用户可能为了“可离线使用”下载当前规则和设备根本不会调用的资源。默认 freestyle 至少需要共享 Rapfi 数据和当前设备使用的一种 WASM 构建；Renju 权重可等用户首次进入连珠模式时再准备。

**建议改法。**拆分“网页已缓存”“当前模式可离线”“所有模式均可离线”三种状态。首次访问只准备当前规则与当前设备的引擎变体；切换到连珠模式时再准备黑白权重。保留一个明确的“下载全部离线资源”选项，满足用户主动要求全模式离线的场景。资源状态应按规则显示，不能在尚未缓存 Renju 权重时误报连珠也可离线。

**验收标准。**干净安装只访问 freestyle 时，不下载 Renju 模型与未选中的 Rapfi 构建；freestyle 能断网继续下棋。首次进入 Renju 后再完成对应模型缓存，随后 Renju 能断网使用。缓存中途失败、空间不足和升级时，在线对局与已有棋局存档不能受损。

**估计工作量：中。**需要调整缓存清单、状态标记、进入模式时的准备流程，并补齐跨规则断网验收。

### 2. P1：给 1 秒以内的搜索设计独立预算策略

**实测依据。**6 秒组覆盖 4 个开局配对、8 盘，自适应为 3 胜、2 和、3 负，得分率 50%；只能说明这组样本没有显示稳定优势。600 毫秒组覆盖另外 6 个开局配对、12 盘，自适应为 3 胜、1 和、8 负，得分率 29.2%；固定搜索得分率 70.8%。自适应平均每步约 388 毫秒，固定搜索约 462 毫秒。详细结果见[6 秒报告](./adaptive-strength-match-v1.md)和[600 毫秒报告](./adaptive-strength-match-v2-600ms.md)。两组预算不同，不能合并计算。

**实现依据。**自适应流程先请求 350 毫秒双候选，再请求 750 / 1400 毫秒主线确认，然后可能搜索对手应手，最后仅在剩余时间超过 180 毫秒时回到完整根搜索（`adaptive-search.js:63–91`）。每一步实际可用时间又受剩余墙钟预算限制（`adaptive-search.js:14–25`）。600 毫秒总预算下，多个阶段会被压缩到很短，部分验证可能无法执行；平均少用约 74 毫秒，却没有维持固定搜索的得分率。

**建议改法。**为短预算设单独策略，不要把 6 秒流程等比例截断。先确保根局面获得足够的完整搜索时间，再根据剩余时间做一次有限复核；若时间不足，明确停止追加候选复核。6 秒流程保持独立，避免短预算的权重调整意外削弱常用深思模式。

**验收标准。**使用同一组棋盘、同一引擎、相同规则和颜色交换，分别对照 600 毫秒、1 秒和 6 秒固定搜索；至少记录胜和负、按颜色拆分、强制胜着 / 必防漏失、平均耗时与未完成复核数。短预算改动先在固定样本上比较前后结果，再扩到新的开局样本；在数据改善前不宣称棋力提升。

**估计工作量：中，评估时间：中。**实现可能很小，但确认棋力不能只靠单元测试，需要重复的真实 WASM 配对赛。

### 3. P1：把现有测试变成合并前自动门，并检查离线清单

**代码依据。**`package.json` 已定义 29 项 Node 测试、JavaScript 语法与引擎 / 模型哈希检查，也有多个浏览器专项 QA 命令（`package.json:7–32`）。目前仓库没有 `.github/workflows`。`scripts/check.js` 核对 JS 语法及引擎、模型和补丁哈希（`scripts/check.js:5–31`），但不会验证 `sw.js` 的缓存清单是否遗漏了新增页面依赖或旧资源。

**用户影响。**一旦遗漏离线文件，联网时功能可能正常，断网后却出现仅部分入口失效的情况；人工本地测试也容易因提交节奏而漏跑。

**建议改法。**先添加快速 PR 工作流：安装锁定依赖，运行 `npm test` 与 `npm run check`。再增加一个离线清单检查，核对入口 HTML 的本地模块 / 样式引用存在且属于缓存策略，检查 `APP_VERSION`、Service Worker release / cache key 的发布约定。Chrome / Edge 专项测试可先作为单独的定时或发布工作流，不必让每个快速 PR 都安装全部浏览器。

**验收标准。**故意制造测试失败、哈希错误或遗漏一个离线依赖时，PR 检查能明确失败；正常变更则自动通过。缓存版本检查要允许共享引擎缓存保持稳定，不能为了 UI 小改动强迫用户重新下载权重。

**估计工作量：小到中。**这是当前最容易快速落地、且会持续降低回归风险的一项。

### 4. P2：为棋局归档补批量备份和手机分享

**代码依据。**归档上限默认为 50 局，数据写入浏览器存储（`game-archive.js:14–41`）。README 明确说明记录只保存在本设备，清理站点数据会丢失；目前可导出单局 JSON / SGF（`README.md:50, 64–66`）。归档页逐项提供导出按钮（`archive-ui.js:10–15`）。

**用户影响。**长期使用时，收藏以外的旧局会被上限淘汰；换手机、清理浏览器或浏览器存储损坏时，用户需要逐局导出，恢复也需要逐局导入。

**建议改法。**先做“导出全部归档”和“验证后恢复归档”两个本地功能：导出文件包含 freestyle 与 Renju 记录、必要的开局计划和 schema 版本；恢复前逐局重放校验，并提供合并 / 替换选择。移动设备用系统分享菜单分享备份文件，浏览器不支持时退回下载。先不引入账号和远端存储，避免为了备份把用户棋谱自动上传。

**验收标准。**导出后清空存储再恢复，最多 50 局、收藏状态、开局流程和未结束对局都可重现；损坏文件不能覆盖当前归档，重复导入不能无提示地产生重复局。

**估计工作量：中。**可以不依赖新后端，适合在 CI 与缓存改进后安排。

### 5. P2：建立真实对局证据闭环

**现状。**附身模式确实面向外部实战：用户录入对手行棋，AI 自动给出我方应手（`README.md:7–9`）。但刚完成的棋力数据是相同引擎和权重的自我对弈，只覆盖固定开局后的普通行棋，不代表真人对手水平，也不测正式开局建议质量。

**建议改法。**在本地复盘流程里提供可选的“标记这是外部对局”与结果标签，基于用户自己的棋谱生成本地汇总：规则、开局类型、执色、最早偏离、AI 建议与实际着法差异、胜负。提供显式导出，不自动上传。真实样本达到一定数量后，再用其构造固定回归局面；不要直接把用户私有棋谱作为在线遥测。

**验收标准。**未标记的用户记录不纳入统计；结果可修正；汇总可删除；分析能明确区分“引擎估值”与“真实胜负”；导出的数据不含账户信息或设备标识。

**估计工作量：中到大。**价值高于再加一个抽象难度档，但依赖用户愿意留存 / 导出对局。

## 四、建议执行顺序

| 顺序 | 工作 | 原因 | 发布门槛 |
|---|---|---|---|
| 1 | PR 自动运行 `npm test` 和 `npm run check` | 成本最低，先保证后续改动不漏基本回归 | 主干 PR 检查必过 |
| 2 | 按模式和引擎变体懒缓存 | 可直接减少移动端首次离线准备的资源量 | 当前模式可离线、跨模式缓存状态正确 |
| 3 | 实现短预算搜索分支并配对复测 | 600 毫秒组暴露了真实质量 / 耗时折衷 | 对照固定预算，没改善就不替换 |
| 4 | 批量归档备份与手机分享 | 保护用户真实棋谱，且无须先建服务器 | 完整往返恢复与损坏文件保护 |
| 5 | 本地真实对局汇总 | 让后续棋力改进来自用户实际场景 | 完全自愿、仅本机、可清除 |

## 五、当前不建议投入的方向

- **不建议现在加新模型或再做一个等级系统。**当前最明确的质量信号是短预算搜索流程与固定搜索的差异，还没有证据说明换模型或扩展设置能解决它。
- **不建议把 600 毫秒和 6 秒成绩合并或称为 Elo。**它们是不同预算、有限样本、同引擎自我对弈，不能代表真人胜率。
- **不建议大规模重写 UI。**项目已有移动、横竖屏、简洁模式、触屏和真实 WASM 的专项验证；本次检查没有发现必须推翻现有界面架构的证据。

## 六、评审边界

本报告基于代码、README、现有专项报告和两批自动保存的真实 WASM 棋谱。没有在本次评审中重新做真实手机网络测试、跨设备实测、真人对局或未公开浏览器兼容测试。棋力判断只使用报告中已完成的 8 盘 6 秒组和 12 盘 600 毫秒组；这两组均为描述性小样本。
